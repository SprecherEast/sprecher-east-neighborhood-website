# Jobs and schedules

> Generated by `npm run docs:generate` from the loaded Payload config (`jobs`), `.github/workflows/`, `.github/dependabot.yml`, `ops/install-cron.sh` and `intelligence/pipeline.yaml`. Do not edit by hand: change the code, then run `npm run docs:generate`.

What runs on a timer inside the application, and in GitHub. Payload starts the runners inside the app’s one process (`jobs.autoRun`), on the first request after a start. A queue with no runner never runs. Timers in browser code (a page checking the version, for example) are not shown. Time zones: the GitHub workflows run in UTC; the job schedules and the server cron set no time zone, so both follow the server’s clock, which this page does not state; the pipeline setting names its own time zone, if it has one. “Collections it reaches” are found by following the handler’s own calls in the source, and those of a schedule’s hooks, with the operation and whether access is checked; a function the config passes in (such as the keepers of the confirmation retention task) is not followed, so a collection reached only that way is not listed; nor are the hooks a write sets off, which can write other collections (the search index, for example): each content type’s hooks are on its own page under Hooks. A collection passed to a shared helper is shown with what the helper does to it where its code shows that, otherwise as “operation not shown”. The calls counted are `find`, `findByID`, `findOne`, `count`, `findVersions`, `findVersionByID`, `findGlobal`, `findGlobalVersions`, `create`, `duplicate`, `update`, `updateOne`, `updateMany`, `updateGlobal`, `restoreVersion`, `delete`, `deleteOne`, `deleteMany`. Where access is bypassed and the code gives a reason, it is quoted below the table. Scheduled tasks that live outside the repository are on [their own page](../knowledge/scheduled-tasks.md), written by hand.

- `deleteExpiredContactMessages`: `form-submissions`, delete and read, from the comment on the function that makes the call: Applies the owner's retention rules to the stored messages (#274), and says how many went.
- `deleteExpiredContactMessages`: `form-submissions`, read, from the comment on the function that makes the call: The addresses that sent a message in the last 12 months.
- `deleteExpiredContactMessages`: `form-submissions`, read, from the comment on the function that makes the call: The messages the rules could delete now, not on hold: unconfirmed ones older than 48 hours, and any older than 12 months. `toExpiredSubmissionIds` makes the decision.
- `deleteExpiredContactMessages`: `forms`, read, from the comment on the function that makes the call: The forms that ask for an email (a handful: all of them are read).
- `deleteExpiredEmailConfirmations`: `email-confirmations`, delete and read, from the comment on the function that makes the call: Deletes the records among `ids` that still match `where`, in one DELETE statement, so the conditions are checked again as the rows go (Payload's `delete` finds first, then deletes each id). Says how many went. …
- `deleteExpiredEmailConfirmations`: `email-confirmations`, read, from the comment on the function that makes the call: Deletes unconfirmed records whose last link went out before `cutoff` (an ISO date), and says how many. A record that got a new link, or was confirmed, in the meantime stays.
- `deleteExpiredEmailConfirmations`: `email-confirmations`, read, from the comment on the function that makes the call: Every record confirmed before `cutoff` (an ISO date): the address and its id.
- `deleteExpiredPasskeyChallenges`: `passkey-challenges`, delete and read, from the comment on the function that makes the call: Deletes the rows of a short-lived collection whose `expiresAt` has passed, with one conditional DELETE, and says how many. Only expired rows go: one still open stays. …
- `deleteExpiredSocialLinkRequests`: `social-link-requests`, delete and read, from the comment on the function that makes the call: Deletes the rows of a short-lived collection whose `expiresAt` has passed, with one conditional DELETE, and says how many. Only expired rows go: one still open stays. …
- `releaseStuckJobs`: `payload-jobs`, read and update, from the comment on the function that makes the call: Before scheduling, puts back in the queue a retention job left "processing", for example by a restart in the middle of a run. Payload 3.91 has no timeout for that, and its default check counts such a job as running, so the task would never be scheduled again and deletion would stop without a sign (#274). …

## Who may queue, run and cancel jobs

| Operation | Function                 | Defined in                      | Route it guards                                                       |
| --------- | ------------------------ | ------------------------------- | --------------------------------------------------------------------- |
| queue     | `isAdminOrEditorBoolean` | `src/platform/payload/roles.ts` | no route in the config                                                |
| run       | `isAdminBoolean`         | `src/platform/payload/roles.ts` | `GET /api/payload-jobs/run`, `GET /api/payload-jobs/handle-schedules` |
| cancel    | `isAdminOrEditorBoolean` | `src/platform/payload/roles.ts` | no route in the config                                                |
