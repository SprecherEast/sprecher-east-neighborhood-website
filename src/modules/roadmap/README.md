# Roadmap

The public plan page: milestones, then epics, then issues, read from GitHub. No collection; the
page is static and refreshes itself. Routes: [screens](../../../docs/reference/routes.md).

## Screens

| Screen                 | Route                                        | Data comes from                                                            |
| ---------------------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| The plan               | `/roadmap`                                   | `getPlan` (GitHub milestones, epic issues and their sub-issues)            |
| One mission            | `/roadmap/missions/[number]`                 | the same plan, `getMission`; the number must be a milestone the plan lists |
| One issue              | `/roadmap/[number]`                          | the same plan, `getPlanIssue`; the number must be one the plan shows       |
| One issue, in a dialog | `/roadmap/[number]` from a click on the plan | the same page's content (`IssueDetail`), shown in a dialog over the plan   |

## Behaviors and events

- GitHub is the only source. The page reads milestones, issues labeled `epic` and each epic's sub-issues over GitHub's REST API (`data/github.ts`); nothing is copied into the CMS, so nothing can drift.
- The plan page's one heading is "What we’re building", in the shared page header at its usual size, with no small label above it (#1082, #1106).
- Both pages are static and re-render every hour (`revalidate = 3600`, `PLAN_REVALIDATE_SECONDS`). Both ask search engines not to index them.
- Screened out, and never shown or counted as shown: issues labeled `infra` or `needs owner`, and any issue whose title or text holds a server address, an email address or a plug-and-play plan. A screened epic takes its sub-issues with it. A milestone left with no shown epic is not listed at all, and comes back by itself when one of its epics can be shown (#1081). A milestone whose title or description fails the screen shows as "Milestone N" with no description. Label names are screened too, and the hidden labels match in any case. The screen is best effort: it finds IPv4 addresses and plain email addresses, not every spelling. The page says how many issues are not shown (`domain/screen.ts`, `domain/plan.ts`).
- Clicking an issue or epic on the plan opens it in a dialog over the plan, and its close button, back button, Escape and the browser's back button return to the plan where it was. A direct visit, a refresh or a shared link shows the issue's own page, so every address works without a script. The dialog and the page show the same `IssueDetail` (`app/(frontend)/roadmap/@modal`, `ui/IssueDetail.tsx`, #946). While the dialog is open the browser tab shows the issue's title, and the site's title returns when it closes; the dialog and the page get their title and "do not index" rule from one function, `planIssueMetadata` (#954).
- A state mark is green for open, purple for done and gray for not planned, each with its words and an icon, in a slightly bigger size than the plain-outline labels beside it, so the state stands out (`ui/IssueBadges.tsx`, #946, #952).
- A screened, unknown or malformed issue number answers 404, so a screened issue can't be reached by its address.
- The numbers at the top and each row's progress count open and done issues; ones closed as not planned are left out of the progress. "Done this week" and "this month" are the last 7 and 30 days in the site timezone (`domain/stats.ts`).
- Activity over time and the order of missions come from one rule (`domain/activity.ts`, #1125). A mission's latest activity is the latest of an issue's close and its last change on GitHub (an edit, a comment, a label), across the mission's issues; the activity picture counts finished issues only. Missions are ordered by it, most recent first, and the first is the one to feature; missions whose issues carry no date come last. A mission whose issues were only edited, not finished, still ranks by that edit. Activity is counted in weeks while at least half of the last 8 weeks are busy (3 or more finished issues across the plan), then in months over the last 6, then in years over the last 3; with no activity at all it stays on weeks. One step and one maximum serve every mission so the tiles compare on the same scale. Weeks are rolling 7-day blocks ending now, months and years are calendar ones in the site timezone.
- A mission (a milestone) has its own page: its name, how many of its issues are done, the activity picture on the plan's shared scale with the numbers written beside it, then one box per project (an epic) that opens to its issues. A project's box links to its own page, and each issue links to its page. An issue row shows its title with its state on the same line, and its number and close date below; labels are not shown on the rows. Titles drop the type prefix developers add ("feat:", "fix(ui):") and start with a capital (`domain/title.ts`). The page is static, refreshes with the plan, asks search engines not to index it and shows only what the plan shows; an unknown, malformed or unlisted mission number answers 404 (`ui/MissionPage.tsx`, #1129).
- Issue text is Markdown shown safely: raw HTML appears as text, only web links open (in a new tab), images show their description only, task lists read "Done" or "Not done", and no issue heading becomes the page's h1 (`ui/IssueMarkdown.tsx`).
- If GitHub can't be read at run time, the render fails, so the last good page stays. During `next build` the plan is empty and the page shows its empty state until the first visit.
- Without a token GitHub allows 60 reads an hour, which an hourly refresh of a larger plan can pass. Set `GITHUB_READ_TOKEN` (read-only) on the server. A wrong token makes GitHub answer 401 and the first render fail ([project facts](../../../docs/project.md)).
- Skipped pull requests: GitHub lists them with issues; the plan drops them.
